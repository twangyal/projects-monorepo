# Native numeric field acceptance — #316

Canonical main implementation: `2ef3885032a4e444de1b1758d8e235a0480d4921`; discoverability follow-up and final application source: `a01453f79baa33b2a97c7bb71ed3b4ba25ca02fe`. [Issue #316](https://github.com/twangyal/projects-monorepo/issues/316) tracks the milestone. No PR was created.

Users can deliberately set a native quantity/numeric form field with “set Quantity number field to 3” or “change number field to -0.25”, then recover with “undo Quantity number field.” Named/deictic clarification, consequential confirmation and cancellation stay shared with the extension. The overlay identifies numeric fields and teaches these commands directly in its help; ordinary text and slider commands retain their meaning.

Literal decimal strings survive interpretation and native assignment. A detached native input checks current min/max/step before live focus/events. The browser's numeric precision governs those constraints; this is not arbitrary-precision arithmetic. Owned identity/value/constraint snapshots, visibility and native/ARIA/inert ancestor guards refuse stale or locked controls. One setter and ordinary input/change events allow website handling; deferred feedback observes retained state. Separate bounded history restores earlier native strings or a previously empty required field, retaining current-limit refusal and ordering across overlapping edits. Custom spinbuttons, number words and units are not converted, and no form submission is requested.
