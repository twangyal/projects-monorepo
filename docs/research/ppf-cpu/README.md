# PPF CPU contact feasibility — #279

Question: does pinned PPF `6b30976f86e6b94d68d459e5237d59704c7d1384` build and execute its small real cloth/cloth contact fixture on a standard Linux CPU runner? This is a research probe outside the shipping app, following [the owner's candidate investigation](../../2026-10-17-clothing-ppf-contact-solver-research.md).

The research workflow builds the real CPU backend with the upstream Cargo.lock and runs the original `tools/cpu_contact_fixture.py` source. Only the documented App.create cache argument is redirected to an explicit empty synthetic cache; geometry, materials, solver calls and all assertions stay unchanged. Two crossed 5×5-vertex sheets produce 13 frames each: contact enabled and contact disabled. Upstream assertions measure actual output segment/triangle crossings, wrong-side vertex frames, motion and the contact-disabled free-fall control. The probe does not replace those gates or claim they independently validate physical fabrics. An initial receipt is written before native execution. The Linux supervisor adopts detached native descendants with PR_SET_CHILD_SUBREAPER and stops/reaps them at the wall limit before collection; a real detached-writer regression checks this boundary. A separate always-run collector retains the native cache, including complete solver stdout/stderr and frames, after a bounded timeout as well as normal completion. Timeout exit codes remain failures, and a successful fixture with missing raw frames fails evidence collection. Forced runner teardown can still prevent cleanup. The JSON receipt records raw held/control measurements, elapsed time, exact revision, fixture checksum and retained synthetic vertex-frame checksums. Logs and process resource receipts remain available even on failure; setup/build success is not contact success.

Reproduce on a CPU host with Rust, a C++ compiler and Python3.12: check out that exact upstream commit; install `warmup.py`'s `python_packages() + tetra_packages()`; run `CARGO_TARGET_DIR=/absolute/upstream/target/cpu cargo build --locked --release --features cpu` in the source tree. With the same target environment, run `python docs/research/ppf-cpu/probe.py --upstream /absolute/upstream --out /absolute/report --cache /absolute/empty-synthetic-cache`. This local workspace has no Rust/CMake toolchain, so actual native execution is delegated to ordinary public Linux CI. No GPU, paid compute, secrets, user garments or remote user uploads are used.

The workflow can be started manually from GitHub Actions; its research-branch push trigger also records this first attempt. It does not run the native probe on every application commit. Dependencies are read from the pinned upstream recipe and their resolved versions are retained; they are not fully hash-locked Python wheels. Stable Rust's actual version and the runner CPU baseline are recorded rather than claimed timeless. `/usr/bin/time` maximum RSS is a per-process maximum, not aggregate concurrent memory.

Initial native run39015923759 built successfully and passed the original fixture, but its implicit-cache search retained no raw frames and only the frontend-truncated native logs. It is preliminary execution evidence, not accepted complete evidence. The corrected run uses an explicit fresh cache, an always-run collector and a tested detached-process bound. Final execution is pending. No PPF engine selection or app integration has occurred. CPU's upstream fixture deliberately uses a dynamic pinned lower sheet; it does not establish static-body collider admission. Coupons/material-unit equivalence, static body and garment/seam admission, one garment/two materials, resolution/timestep studies and independent physical references remain prerequisites before a backend decision.
